# 设计取舍

这份文档记的是"为什么这样做"，以及"这样做之后实测到什么"。所有数字来自
`results/eval_report.json`，可用 `python -m ragmini.cli eval` 复现。

## 0. 问题边界

做的是**检索质量**这一层：给定一条中文问题，从 99 条条款里找出该引用的那一条，并且能判断"库里到底有没有"。

不做的是生成质量评测。原因写在 README「还没做的」：没有 judge 模型的一致性校准，报 Faithfulness 只是把不可复现的东西包装成结论。

语料规模刻意控制在 3 篇 / 99 条：小到能一眼看完，大到足以让"相近条款互相干扰"这件事出现（甲类仓库 30 米 vs 乙类 20 米、技师 2 张 vs 高级技师 3 张、返修 30 天 vs 总成 90 天）。

## 1. 切分：为什么按条款切

**不按定长切（512/200/overlap 50）的原因**：规范类文本里，"第 5 条"和"第 6 条"讲的是两件不同的事。定长切会把第 5 条的结尾和第 6 条的开头拼进同一个块，检索命中后模型看到的是两段不相干的义务，答出来的东西"像那么回事但不对"。这类错误在评测里看不出来（命中率正常），只有人工看 badcase 才发现。

**条内再切 leaf（默认 60 字）**：第一版设的 120 字，结果 54 条语料的平均长度只有 71 字，`leaf == parent`，父子分块形同摆设。改成 60 后 99 条切成 171 个 leaf，检索粒度才对得上。

这个参数不是"越小越好"：切太碎会把"条件 + 结论"拆开（"电量低于 15% 时" 和 "强制退出任务队列" 分到两块），单块命中后语义不完整。60 字大约是一条规程的"一个完整义务"。

**父子分块的价值**：命中 leaf 只说明"这句相关"，生成要的是整条。`retrieve.py` 里 `Hit` 同时带 `leaf_text`（用于打分和展示命中片段）与 `text`（父块，用于拼上下文）。不做这一步，模型经常拿到半句话。

## 2. 召回：dense 与 sparse 各补什么

实测（`by_type` 里的 `paraphrase` 分项）：

| 模式 | paraphrase Hit@5 | 解释 |
|---|---|---|
| dense | 1.000 | "多快必须给出方案"能对上"应在 2 秒内返回" |
| sparse | 0.750 | 字面没有"多快""必须给出"这些词，BM25 召不回 |
| hybrid | 0.875 | 融合救回一部分，但名次被 dense 的强候选挤住 |
| hybrid+rerank | 1.000 | 精排按"能不能回答"重新排，救回全部 |

反过来，**纯 dense 在强术语问题上并不吃亏**（numeric 类 37 条全中），因为 BGE-M3 对中文数字条款的语义匹配已经够好。所以在小语料上 dense 看起来"已经够用"——这是小语料的局限，不是 dense 的上限；真实场景里型号、编号、专有名词多的库，BM25 的价值会明显得多。

保留 BM25 的另一个理由不是效果，是**可解释性**：当用户问"为什么这条没搜到"，能说清是"词没匹配上"还是"语义没对上"。

## 3. 融合：为什么用 RRF，不用加权分数

$$\text{score}(d) = \sum_{r \in \text{rankings}} \frac{1}{k + \text{rank}_r(d)},\quad k=60$$

- **不用加权求和**：余弦在 0–1，BM25 无上界且随 query 长度变化。要先归一化，而归一化方式（min-max / z-score / 除以最大值）本身又是超参，调起来没有依据。
- **k=60 的作用**：压平头部差异。k 小（如 10）时第 1 名和第 2 名的分差很大，等于让某一路"说了算"；k 大时各路贡献接近平均。60 是 RRF 原论文的经验值，本文没做敏感性扫描——**这是没验证的部分，不要说得比实际更确定**。

**一个反直觉的实测结果**：hybrid 的 Hit@5（0.980）比纯 dense（1.000）**低**。原因是 RRF 按名次累加，某条被 dense 排第 1、被 BM25 排第 30 时，融合后可能掉到第 6；而另一条两路都排第 3 的会上来。名次融合优化的是"两路都认可"，不是"某一路很确信"。

这个损失由重排补回来了（Hit@5 回到 1.000）。**如果只上融合不上重排，在这份语料上是负收益**——这一点如果不实测是发现不了的。

## 4. 重排：cross-encoder 的账

- **为什么有效**：双塔（bi-encoder）把 query 和 document 分别编码，两者在编码时互相看不见，只能靠向量空间对齐；cross-encoder 把 `[query, passage]` 拼成一个序列送进模型，注意力能直接建模词级交互。代价是不能预计算——每个 (query, doc) 都要跑一次前向。
- **为什么只重排 top-10**：171 个 leaf 全量重排 = 171 次前向，单条 query 从 ~20ms 涨到 ~1.2s。取前 10 时 recall 已经饱和（实测 failures 为 0），再多是白花钱。
- **实现细节**：没有用 `sentence_transformers.CrossEncoder` 封装，而是 `AutoModelForSequenceClassification` + `AutoTokenizer` 直连。原因很实际：`bge-reranker-large` 只提供 sentencepiece 词表，封装层会去找 `AutoProcessor` 能识别的文件然后报错。直连还能顺手讲清原理——取 `[CLS]` 位置的 logit 过 sigmoid。

**重排提升的具体位置**：MRR 0.983 → 0.987、nDCG@5 0.980 → 0.990。提升不大，因为 dense 本身已经把 gold 排在第一（Hit@1 0.960）。重排真正的价值在拒答判定上——不是"准确率更高"，而是"阈值更稳"，见下一节。

## 5. 拒答：判定分和排序分不是一回事

这是整个项目里返工最多的一节，因为**第一版结论是错的，改对之后又发现第二版结论只对了一半**。

### 5.1 第一版：阈值 0.35，一条都没拒

初始设计用 dense 余弦 + 阈值 0.35 判拒答，实测拒答准确率 **0.000**。看分布才明白为什么：

| 信号 | 可答组 | 不可答组 | 重叠 |
|---|---|---|---|
| dense 余弦 | min 0.565 / p10 0.698 / median 0.779 | min 0.512 / median 0.574 / max 0.700 | **0.565–0.700，几乎贴在一起** |
| 精排 sigmoid | min 0.232 / p10 0.958 / median 0.997 | min 0.001 / median 0.024 / max 0.858 | 只在个别样本上重叠 |

原因是语义层面：同一份规程里，"仓库租金多少钱"和"仓库防火间距"的向量确实很近——都在讲仓库。余弦衡量的是"话题相近"，而拒答要判断的是"这段材料能不能回答这个问题"。

### 5.2 第二版：把阈值标对，余弦其实也能判

上面这张表容易读成"余弦没用"，但这是**阈值取错**造成的误判。0.35 远低于不可答组的中位数 0.574，自然一条都拒不掉。把阈值扫一遍：

| dense 阈值 | 误拒率 | 拒答准确率 |
|---|---|---|
| 0.55 | 0.000 | 0.278 |
| 0.58 | 0.020 | 0.500 |
| 0.60 | 0.020 | 0.667 |
| 0.62 | 0.020 | 0.889 |
| 0.65 | 0.040 | 0.944 |

| 精排阈值 | 误拒率 | 拒答准确率 |
|---|---|---|
| 0.20 | 0.000 | 0.833 |
| 0.50 | 0.020 | 0.889 |
| **0.70** | **0.020** | **0.944** |
| 0.85 | 0.020 | 0.944 |

两条曲线形状完全不同：**dense 在 0.60–0.65 这五个点里从 0.667 跳到 0.944，而精排从 0.20 到 0.70 是一个缓慢上升的平台。** 同样到 0.944，dense 要付出 0.040 的误拒，精排只要 0.020。

### 5.3 第三版：交叉验证，0.944 会掉到多少

上面所有数字都是 **in-sample**：阈值在同一份 68 题上扫出来，指标又在这 68 题上报。这是典型的自适应过拟合。改成两折交叉（评测集按 `type × answerable` 分层切 A/B，A 折的阈值只用 B 折选，反之亦然）：

| 信号 | in-sample（全量标定） | 两折交叉（样本外） |
|---|---|---|
| dense 余弦 | 0.944 | **0.889** |
| 精排 sigmoid | 0.944 | **0.889** |

两件事同时成立，而且都值得讲：

1. **0.944 → 0.889 就是过拟合的幅度**：18 条不可答样本里差 1 条。样本量这么小，这个差不能当成"信号优劣"的证据。
2. **交叉验证后两者打平**——所以"精排判拒答更准"这个说法，在这份数据上站不住。站得住的是**阈值稳定性**：dense 的可用区间只有 0.02 宽，语料一漂就得重标；精排的区间宽得多。

**工程上的原则**（比"用精排分、不用余弦"更准确）：判定用精排分，不是因为它更准，而是因为它的阈值容错更高。排序分本身就是"话题相近度"，跟"能不能答"是两个问题，只是精排把这个差距拉得更容易设阈值。

### 5.4 剩下的失败样本

漏拒的那 1 条是"空压机的保养周期"——被"举升机每日点检"蹭到，属于同领域同句式的干扰。真实系统里这一层还要再加一道"答案必须带引用、且引用必须落在被引条款上"的检查。

## 6. 评测口径

- **gold 按条款 ID 匹配**（`demo-01-dispatch#第4条`），不做文本相似度匹配。相似度阈值匹配会让"命中"这件事变得可以自我解释。
- **不可答问题必须进评测集**。只测可答问题，系统会越来越倾向"总能给个答案"，而这在生产里是最危险的失败模式。
- **误拒和漏拒分开报**。合成一个 F1 会掩盖两边的代价不对称：误拒让用户觉得系统没用，漏拒让用户拿到错误答案。
- **每个模式跑同一套 68 题**，只改检索策略，不改评测集。
- **阈值必须样本外标定**。所有对外报的拒答指标都走 `--cv`（两折交叉）：A 折的阈值只用 B 折选。in-sample 数字保留在 `results/eval_report_insample.json` 里，只用来量化过拟合幅度，不作为结论。
- **fold 按 `type × answerable` 分层**，不随机切。随机切会让某一折的不可答样本落到 5 条，拒答准确率的分辨率变成 1/5，比结论本身还大。

## 7. 工程取舍

| 决定 | 代价 / 何时该换 |
|---|---|
| numpy 全量点积，不上 FAISS | 171 条时一次 matmul < 1ms。上万条后需要换，接口就是 `VectorIndex.search` |
| 自实现 BM25（30 行） | 少了 `rank_bm25` 依赖，也便于讲清 k1/b。语料上百万时要换倒排索引 |
| 模型懒加载 | 评测要跑四种模式，加载一次复用；代价是首次查询慢，所以给了 `build()` 预热 |
| 每次启动重建索引 | 换语料即生效，适合演示。生产要落盘 + 增量 |
| `tfidf` / `lexical` 降级后端 | 保证"没有 GPU 也能验证链路"，但指标不能与 BGE-M3 混着报 |

## 8. 已知局限

1. **语料小**：99 条，dense 已经接近饱和（Hit@5 1.000）。混合检索的收益在这个规模上主要体现在改写型问题与拒答，不能外推成"真实业务上也只能提升 2 个点"。
2. **k=60 没做敏感性扫描**，直接用了论文经验值。
3. **重排模型与语料同域**：bge-reranker-large 在通用中文上训练，这份语料也是通用书面语，所以分数偏乐观。领域黑话多的库需要重测。
4. **没有做 query 改写**：多轮对话里的指代（"那它呢"）现在会直接检索失败。
5. **两折交叉不是终点**：折的划分由我按类型分层手工决定，不是随机重复 K 次取均值。严格做法是 5 折 × 多次重复，68 条撑不住。所以 0.889 也只是"比 0.944 更可信"，不是无偏估计。
5. **生成侧未评测**：`answer.py` 里的 LLM 路径可用，但没有指标支撑，不建议在面试里把它当成果讲。
